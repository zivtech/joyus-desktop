### Open — found while writing the plans

- **D8 — Who owns secrets?** The UI saves credentials through the sidecar into `~/Library/Application Support/com.joyus.desktop-companion/credentials.env` (mode 0600) and reads them back from there. Separately, the Rust shell runs a startup migration that copies that file into the keychain and deletes it. Today the keychain is a no-op mock, so the migration always fails verification and keeps the file. **If anyone enables the keychain backend, the next launch deletes the file the UI reads: saved credentials vanish from the UI, the user re-enters them, and from then on both stores exist with the plaintext file permanent.** Options: (a) the Rust shell and the OS keychain own all secrets, and the sidecar receives values per call; (b) admit the file: remove the keychain module, the migration and the `keychain_*` commands, and document the 0600 file. Recommendation: (a), planned after PR #5 so it can be checked on a running app. Until then, do not add a `keyring` feature flag.
- **D10 — Should a crashed MCP server be restarted?** The names in `@joyus/mcp-registry` say yes (`startWatchdog`, `maxRestarts`, `restartCount`), but an exited process is removed from the table before the watchdog runs, and the callback in `services.ts` restarts nothing. Decide whether auto-restart is wanted before anyone plans it.
- **D11 — What is "config"?** `Settings.tsx` calls `get_config` with no key and expects `{ autoStart, telemetryEnabled, version, buildDate }`, and sets booleans. `Onboarding.tsx` and `App.tsx` read and write string keys (`onboarding_complete`, `onboarding_phase`). `Onboarding.tsx` also writes `auth_token` through `set_config`, a secret that nothing ever reads back. The Rust commands accept only `key: String` and `value: String`. A contract is needed before the sidecar methods are written. Proposed: `config.get { key? }` returns one value or the whole object; `config.set { key, value }` takes any JSON scalar; a fixed list of allowed keys that excludes `auth_token`; the UI stops writing the token.

## Review notes on PR #5 (`fix/linux-desktop-onboarding`, head `54fb205`, read in full 2026-11-17)

These are for the maintainer's review of that pull request. No plan here changes its files.

1. **A server command that cannot start kills the sidecar.** `entry.ts` wraps `child_process.spawn` without an `error` listener. A missing executable in `~/.joyus/servers.json` emits `error`, which becomes an uncaught exception, which `startSidecar` treats as fatal.
2. **`pid: child.pid ?? -1` is a dangerous sentinel.** Today finding 1 exits the process first. If someone fixes finding 1 by adding an `error` listener and leaves the `-1`, `processManager.stopServer` will, after its 5-second timeout, call `process.kill(-1, "SIGKILL")`. On POSIX, pid `-1` means every process the user owns. Node passes it through (`process.kill(-1, 0)` returns `true`). Fix both together: never return `-1`, and have the process manager refuse a non-positive pid.
3. **Quit paths other than the tray leave the sidecar running.** Closing the window now hides it (correct), and only the tray's Quit item calls `shutdown_sidecar`. Cmd+Q, an updater restart or a crash do not. The sidecar has no handler for its stdin closing, and its timers keep it alive.
4. **`entry.ts` is excluded from coverage but contains real logic** (manifest parsing, the spawn wrapper, the kill wrapper). Plan 015 exercises it.
5. **`readManifest` trusts the file's shape.** A `servers.json` without a `servers` key makes `createRegistry` throw during startup.
6. **First window, no content security policy.** `tauri.conf.json` gains a window but no `app.security.csp`, while `keychain_retrieve` returns secret values to the webview and `shell:allow-open` is granted.
7. The argument-name fixes (`engagementId`, `{ params: ... }`) are consistent with the Rust signatures. The Rust changes in this pull request have never been built by CI; plan 011 adds that job.

### New findings from the revision work, not planned yet

- **F19 — a registry file of the wrong shape blocks every reconcile.** `readRegistry` casts whatever JSON it parses. A file that holds `{}` or a string has no `entries`, and every `reconcile()` then returns `rolled_back`. Run on 2026-11-18 against the code before and after plan 012: same result. Small fix: treat such a file as missing, which triggers repair.
- **F20 — a unit test writes into the real home directory.** `apps/desktop-companion/test/sidecar/mainConfigCheckWiring.test.ts` calls `startSidecar` without a session wiring override, which opens `~/.joyus/session-manager.db`. Seen as `.joyus/session-manager.db` in the throwaway home on every scratch run.
- **F21 — worktree health checks compare unresolved paths.** `isWorktreeHealthy` in `worktreeManager.ts` and its twin in `taskBranchStore.ts` look for the stored path in `git worktree list`, which prints resolved paths. For a repository under a symbolic link, including every path under `/tmp` on macOS, a healthy worktree would be reported as missing, and `resume` would mark the session broken. The listing difference was measured; the health check itself was not run in that situation. Plan 016 adds the path resolver it would need.
- **F22 — a non-forced delete of a broken session runs `git status` in the wrong folder.** A session whose worktree could not be created is stored with an empty worktree path, and `hasUncommittedChanges` passes that path as the working directory. Read from the code, not run.
- **Open question from plan 013.** When `SKILL_SYNC_BUNDLE` names a bundle that the manifest no longer has while other bundles remain, and no earlier manifest is in memory, sync can never succeed. Revocations are applied, nothing is ever added, and the cycle is retried every five minutes. Before plan 013 the same manifest was simply never acted on. Whether a missing configured bundle should count as "nothing to sync" is a product decision.
- Test files are not typechecked (`tsconfig.json` excludes `**/test/**`). Four type errors exist in `packages/session-manager/test` and one in `configCheckWiring.test.ts`, all older than these plans.

What the review got right about method: the plans' examples encoded the intended cases and did not test collisions, transitions or failed verification. Plans 009, 010 and 012 each missed something that running the code found at once, and the revisions of 013 and 016 found more the same way. A plan that prescribes non-trivial code gets a reference implementation that passes the package's existing tests, and a replay of the written plan, before it is published.

The November findings were reviewed by a second model (Gemini 4 Argon, high effort) before any plan was written.
