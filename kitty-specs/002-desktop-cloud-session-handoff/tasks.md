# Work Packages: Desktop-to-Cloud Session Handoff

**Inputs**: Design documents from `/kitty-specs/002-desktop-cloud-session-handoff/`
**Prerequisites**: plan.md (required), spec.md (user stories), research.md, data-model.md, contracts/handoff-api.yaml, quickstart.md

**Tests**: 100% line/function/branch/statement coverage is mandatory per constitution principle 2.5. Every WP includes its own test subtasks.

**Organization**: Fine-grained subtasks (`Txxx`) roll up into work packages (`WPxx`). Each work package is independently deliverable and testable.

**Prompt Files**: Each work package references a matching prompt file in `/tasks/` generated by `/spec-kitty.tasks`.

## Subtask Format: `[Txxx] [P?] Description`
- **[P]** indicates the subtask can proceed in parallel (different files/components).
- Include precise file paths or modules.

## Path Conventions
- **Shared packages**: `packages/policy-client/src/`
- **Desktop app**: `apps/desktop-companion/src/`
- **Tests**: Co-located `*.test.ts` files

## Phase 3: Encryption

## Work Package WP04: E2E Encryption & Chunking (Priority: P1)

**Goal**: Encrypt the session snapshot using hybrid ECIES (X25519 + AES-256-GCM) with per-chunk integrity and anti-reordering.
**Independent Test**: Encryption round-trips correctly; tampered or reordered chunks are rejected.
**Prompt**: `/tasks/WP04-encryption-and-chunking.md`

### Included Subtasks
- [ ] T014 Implement ECDH key agreement (X25519) and CEK derivation (HKDF-SHA256) in `packages/policy-client/src/snapshotEncryption.ts`
- [ ] T015 Implement per-chunk AES-256-GCM encryption with unique IV per chunk
- [ ] T016 Implement sequence-number AAD binding (sessionId + chunkIndex + totalChunks)
- [ ] T017 Implement fixed chunk boundary splitting (5 MiB default, 256 KiB aligned)
- [ ] T018 [P] Implement per-artifact encryption (same CEK, independent IV per artifact)
- [ ] T019 Write tests: round-trip, tampered chunk, reordered chunk, chunk boundaries, deterministic test vectors

### Implementation Notes
- Use Node.js Web Crypto API for X25519 (requires >=22.13 or >=20.19).
- Key agreement: receive cloud X25519 public key → generate ephemeral desktop key pair → ECDH shared secret → HKDF-SHA256 → 256-bit CEK.
- Each chunk gets unique 12-byte IV (random) + AAD = `${sessionId}:${chunkIndex}:${totalChunks}`.
- Chunk boundaries: `Math.ceil(totalSize / chunkSize)` where chunkSize = 5 MiB (5,242,880 bytes).
- Test vectors: use fixed key pairs from research.md for reproducible tests.

### Parallel Opportunities
- T018 (artifact encryption) can proceed alongside T015-T016 (chunk encryption).

### Dependencies
- Depends on WP01 (types) and WP02 (snapshot assembly — to know what to encrypt).

### Risks & Mitigations
- X25519 Web Crypto API stability → pin Node.js version in CI, add runtime version check.
- GCM nonce reuse catastrophe → unique random IV per chunk, never reuse.

## Phase 4: Transport (parallel pair)

## Work Package WP05: Resumable Upload Client (tus) (Priority: P1)

**Goal**: Desktop-side tus client for uploading encrypted chunks and artifacts with retry and resume.
**Independent Test**: Uploads complete successfully; retries on failure; resumes from last offset after exhaustion.
**Prompt**: `/tasks/WP05-resumable-upload-client.md`

### Included Subtasks
- [ ] T020 Integrate `tus-js-client` for encrypted chunk upload in `apps/desktop-companion/src/handoffUpload.ts`
- [ ] T021 Implement parallel artifact uploads via separate tus endpoints
- [ ] T022 Implement retry with exponential backoff (1s base, 30s cap, configurable max retries)
- [ ] T023 Implement resumable fallback (HEAD to discover offset, resume from last position)
- [ ] T024 Implement upload progress tracking for state machine updates
- [ ] T025 Write tests with mock tus server

### Implementation Notes
- `tus-js-client` handles chunked upload protocol; configure with 5 MiB chunk size.
- Parallel artifact uploads: each artifact gets its own tus upload URL from `initiate_handoff` response.
- Exponential backoff: delay = min(baseDelay * 2^attempt, maxDelay). Default: 1s base, 30s cap, 5 retries.
- Resume fallback: after retry exhaustion, issue HEAD request to get current offset, create new tus upload from that offset.
- Progress events feed into state machine for UI updates.

### Parallel Opportunities
- WP05 and WP06 can run in parallel (different modules).

### Dependencies
- Depends on WP01 (types) and WP04 (encryption — encrypted data is what gets uploaded).

### Risks & Mitigations
- tus protocol overhead for small sessions → acceptable, chunking adds minimal overhead.
- Mock tus server fidelity → use `@tus/server` as test harness for realistic behavior.

## Phase 5: Integration

## Work Package WP07: Handoff Orchestrator (Priority: P1)

**Goal**: Top-level coordinator wiring together authorization, encryption, upload, and state management into the complete handoff flow.
**Independent Test**: Full handoff happy path completes; each failure mode transitions to `failed` state with correct error.
**Prompt**: `/tasks/WP07-handoff-orchestrator.md`

### Included Subtasks
- [ ] T031 Implement orchestrator in `apps/desktop-companion/src/handoffOrchestrator.ts`
- [ ] T032 Wire state machine transitions at each orchestration step
- [ ] T033 Implement error handling and user notification for each failure mode
- [ ] T034 Implement timeout management (30-second SLA awareness)
- [ ] T035 Implement concurrent handoff prevention (reject if already in progress)
- [ ] T036 Write tests for happy path, each failure mode, timeout, and concurrent rejection

### Implementation Notes
- Orchestration sequence: initiate → authorize (WP03) → encrypt (WP04) → upload (WP05) → complete (WP06).
- State machine drives each transition; on any error, transition to `failed`.
- Timeout: if total elapsed exceeds configurable threshold (default 30s), abort and transition to `failed`.
- Concurrent prevention: track active handoff per session; reject new attempt if one is in progress.
- User notifications: success → pickup_url; failure → actionable error message.

### Parallel Opportunities
- None — this is the integration WP that wires everything together.

### Dependencies
- Depends on WP01-WP06 (all prior WPs).

### Risks & Mitigations
- Integration complexity → test with stubs for each sub-module; add integration test with all real modules.
- Timeout races → use AbortController for clean cancellation.

## Work Package WP08: Cloud Snapshot Verification & Session Reconstruction (Priority: P2)

**Goal**: Define cloud-side contract expectations for snapshot verification and session reconstruction, with test doubles for integration testing.
**Independent Test**: Verification rejects tampered/incomplete snapshots; reconstruction produces complete session state.
**Prompt**: `/tasks/WP08-cloud-verification-and-reconstruction.md`

### Included Subtasks
- [ ] T037 Define verification contract in `packages/policy-client/src/handoffVerification.ts`
- [ ] T038 Define session reconstruction contract
- [ ] T039 Implement test doubles simulating cloud behavior
- [ ] T040 Write tests for verification, rejection, and reconstruction

### Implementation Notes
- Verification: decrypt chunks using derived CEK, verify GCM auth tags, check AAD sequence numbers, validate manifest against received data.
- Reconstruction: deserialize decrypted snapshot into cloud session state (conversation history, pending actions, artifacts).
- Test doubles simulate the cloud side for desktop integration tests — accept valid snapshots, reject tampered ones.
- This WP produces contracts and test doubles, not the actual cloud implementation.

### Parallel Opportunities
- None — this is the final verification WP.

### Dependencies
- Depends on WP01 (types) and WP04 (encryption — for decryption counterpart).

### Risks & Mitigations
